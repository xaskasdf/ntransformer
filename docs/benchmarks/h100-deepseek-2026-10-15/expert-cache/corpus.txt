Transformer inference is a sequence of dependent computations. A request begins with a prompt, and the model processes its tokens to construct attention state. Once this preparation is complete, it predicts a new token, appends that token to the history, and repeats the process. The time to the first token and the time between later tokens describe different parts of the user experience.

An inference engine must place weights, activations, and cached attention data somewhere in the memory hierarchy. Some values remain on the accelerator, while others move from system memory when they are needed. A mixture of experts selects a small subset of its expert networks for each token. Keeping frequently selected experts in device memory can reduce transfers, but the usefulness of this cache depends on the actual sequence of requests and on the capacity available.

Consider an experiment with one request at a time. The first execution starts with an empty device cache for experts. The same prompt and the same deterministic continuation are then executed again. The later runs reuse cached weights, but they rebuild the attention state from the beginning. This separates weight reuse from reuse of a previously computed prompt. Both measurements are useful, provided that their conditions are stated clearly.

Longer prompts can touch a wider set of experts. Once that working set exceeds the cache capacity, previously loaded weights must be evicted to make room for new ones. A repeated request can therefore continue to transfer data even after its first execution. Calling such a request warm does not imply that every access will hit in device memory. The cache counters and transfer bytes are needed to explain the measured throughput.

A careful benchmark also distinguishes processing work from output formatting. Tokenization takes place before the prompt is evaluated. Selecting a predicted token examines the output scores. Printing the selected text, writing logs, and validating numerical results can add their own costs. Recording these boundaries makes the timing easier to reproduce and prevents unrelated work from being mistaken for accelerator computation.

The most useful optimization depends on the largest remaining cost. If expert transfers dominate, improving residency or overlapping transfers with computation may help. If computation dominates, kernel scheduling and arithmetic efficiency become more important. If the host spends much of its time coordinating small operations, removing dispatch overhead can improve latency without changing the model. The first step is to measure the complete execution path and identify which of these conditions applies.

For a practical report, record the model files, quantization formats, software revision, accelerator model, cache budget, prompt tokens, and generation length. Keep the input token IDs and the generated text alongside the raw timing samples. Report the first execution separately from repeated requests and describe whether the end-of-sequence token was allowed to terminate generation. These details make a performance number understandable and reproducible.

The results should guide the next experiment. A smaller isolated kernel can reveal an arithmetic bottleneck, while an end-to-end request shows whether fixing that kernel improves the experience of using the model.
